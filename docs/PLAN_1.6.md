# Rin NPU Agent 1.6 计划

日期：2026-09-06。状态：1.6.0-alpha.1 独立测试 APP 已构建，等待手机 NPU 验证。正式 WAI LoRA 和普通词 embedding 加权尚未接入。稳定基线为用户已确认生图成功的 1.5.11 / code 17。正式版本号采用 1.6.0，后续修复使用 1.6.1 等命名。

## 目标与边界

1.6 有两条开发主线：LoRA 为最高优先级，实时预览并行推进但优先级低于 LoRA。主要开发时间用于 LoRA 的真实加载、权重控制和兼容性。LoRA 达到验收条件后可以先出测试版，不因预览尚未完成而等待；历史、取消、诊断等附加功能也不阻挡 LoRA。保留 1.5.11 的可用生图链、历史签名、用户数据及已下载模型。APP 开发、构建、发布均在 desktop；只有确需重新准备生图模型时，才由 workstation 承担模型编译。每阶段验收后再进入下一阶段。

## LoRA 文件与界面

LoRA 原文件统一放在现有运行时的子目录 `Download/sdxl_qnn/Lora/`，不在 Download 根目录另建同级 LoRA 文件夹。路径由当前 runtime base 派生；适配缓存单独放在 `sdxl_qnn/.rin_lora/cache/`。APP 接入后在已取得存储权限的前提下创建目录。用户放入 `.safetensors` 或通过系统文件选择器导入；清理缓存不删除原文件，也不自动移动已有文件。

进入页面、返回前台及手动刷新时检查文件变化，在后台扫描。可增加文件变动监听，但以实际重新扫描为准。未下载完成、仍在写入或文件头不完整的文件不标记为可用。首次读取头信息和张量键，校验目标架构、模块、秩与当前后端能力；同名文件用稳定 ID 区分，不能仅靠文件名判断兼容。

列表显示名称、兼容状态、大小、权重与可编辑触发词。状态至少区分“可用”“首次适配中”“待适配”“不兼容”。兼容性不明时明确显示待验证；不能把能读取文件等同于已能作用于 NPU。

直接输入是主要操作方式，例如 `<lora:角色:0.8>`、`<lora:画风:1.1>`，不要求先点选再调整。省略权重时用 1.0，0 表示不施加该 LoRA 的权重增量。列表点选仅用于快捷插入标签，滑条是可选辅助，必须与文字中的权重双向同步。同一 LoRA、同一权重去重；冲突权重在生成前报错，不默默累加。扫描不会自动激活全部文件。中文名和空格使用稳定映射，重名文件不能随便选择。

生成前将 LoRA 控制标签解析为结构化请求，从 CLIP 普通提示词中移除。触发词可从可信元数据读取并允许用户编辑，不猜测不存在的触发词。请求和历史记录保存 LoRA ID、文件 hash、实际应用权重与受影响模块。

## 普通提示词权重

普通词组支持 `(red hair:1.1)`、`(blue eyes:0.8)`；逗号分隔的 `red hair:1.1, blue eyes:0.8` 作为快捷写法，由应用归一到同一解析结果。数字比例和 URL 不按 tag 权重处理。嵌套括号需有明确规则与边界，非法或非有限权重在生成前提示。

LoRA 强度、普通词权重和全局 CFG 分别处理。LoRA 标签解析后不送入 CLIP；普通词权重须正确对齐两个 CLIP 的 token/embedding，不能仅删除括号后当作实现完成。CLIP 缓存键必须包括解析后的词权重，以及作用于 text encoder 的 LoRA 身份、内容校验值和强度。原型当前仅完成解析，还未接入 CLIP 加权推理。示例中的角色名只是别名，不代表底模自动具备中文语义能力。

## LoRA 执行方案与验收

当前代码的 `--lora-slot` 仅切换预编译 UNet context，尚未实现任意用户 LoRA 权重加载。当前 QAIRT 2.48 SDK 提供 Android `libQnnLoraAdapterBinUpdater.so` 和 `QnnContext_applyBinarySection`；更新器需要适配模板、DLC 转换信息和既有 adapter binary。官方 LoRA 流程还提供浮点权重更新路线。这些构成可验证的实现候选，不能据此直接认定所有 SDXL LoRA 已兼容。

当前优先验证动态 A/B 输入路线：底模一次编译，LoRA 的矩阵和强度作为输入。手机实测通过后，才扩展到 WAI 的实际模块、秩和多 LoRA；预编译 adapter binary 作为对照及候选优化路线保留。SDK 更新器路径在本轮小图中存在编译错误，尚不能作为唯一依赖。应优先保持现有浮点生图质量。不能把每个 LoRA 重编一套数 GB UNet 作为默认用户流程；若验证发现只能采用预编译包，应先重新确认交付方案。

首期面向当前 WAI / Illustrious SDXL 的普通 LoRA。SD1.5、Flux、SD3 与当前模型不混用；LyCORIS、LoHa、LoKr、特殊卷积或未支持的 text encoder 更新应显示具体状态，不能静默丢弃部分权重。先验证单 LoRA，再验证两项 LoRA 的组合和独立权重。包含 CLIP 修改的 LoRA 必须覆盖相应 CLIP 更新和条件缓存失效策略。

验收使用固定提示词和 seed：关闭 LoRA、权重 0、权重 0.4/0.8、重新关闭及重新启用。权重 0 应在确定性容差内恢复基线；非零权重应有真实 adapter/tensor 应用证据及预期效果，不能仅以日志显示“已加载”为成功标准。未支持的文件、层或秩须在生成前明确反馈。双 LoRA 需分别禁用和调整权重，排除结果缓存或请求串线。

## 实时预览

现有开关按预览模型文件是否存在启用，未覆盖完整解码验证。1.6 应准备匹配 SDXL 的轻量预览解码器，例如 TAESDXL，按需下载，并核对布局、精度和 latent 缩放。不能误用 SD1.x 的 TAESD 权重。

提供关闭、流畅、低频三个档位。8 步时先以每 2 步一次为默认候选，另设每 4 步一次；只有完整预览链通过实机检查后，才默认启用。预览队列只保留最新待处理帧，每帧关联本次生成 ID，防止旧图闪回。主模型推理优先，预览失败或资源不足时跳过预览，继续最终图片生成。最终图仍使用正式 VAE，不以轻量预览替代。

同 seed 对比预览开关前后的最终输出、总耗时和峰值内存，记录实测额外开销。15% 以内可作为性能目标，不是已达到的承诺。若达不到，降低频率、分辨率或调整解码后端。

## 同期实用功能

| 优先级 | 功能 | 验收重点 |
|---|---|---|
| P0 | 生图历史与参数复用 | 持久保存结果，记录正负提示词、seed、步数、CFG、模型与 LoRA；一键复用，应用重启后可读 |
| P0 | 一键导出诊断 | 自动打包本次阶段日志和版本信息；分享前预览，提示词等私密内容可排除 |
| P1 | 停止与资源状态 | 显示真实阶段和每步耗时；取消后不再启动后续步骤，确认清理完成后才能接收新任务 |
| P1 | 参数控制 | 保留 8 步稳定默认，补 seed 锁定、随机/递增种子；只开放实际模型支持的设置 |
| P1 | 组件管理 | 显示底模、修复包、预览器、LoRA 缓存大小；定向修复损坏组件，不把清缓存变成删模型 |
| P2 | 性能整理 | 减少重复 context 加载与中间磁盘 I/O，保留正常/详细日志档位；优化前后做实测对比 |

暂不同时扩展多芯片、任意分辨率、ControlNet 或视频生成，避免把本轮 LoRA 和预览验收拖成另一个工程。

## 双主线与验收顺序

A 线为 LoRA。先完成可更新模型、适配器二进制和实际权重生效，再接入文件夹扫描、直接标签、强度、缓存和覆盖安装。优先让一份用户真正想用的普通 SDXL LoRA 跑通，再扩展两个 LoRA 的组合与 text encoder 更新。每个节点分别验收，不把原型通过当成整版完成。

B 线为实时预览。独立准备 TAESDXL、组件下载和解码测试，在不会修改 A 线共享文件的前提下推进。共享运行时由同一集成步骤修改；并行目标不等于两个任务同时覆盖同一源码。主生图优先，预览失败不阻断最终生成。当前这轮只实施 A 线原型，B 线尚未写代码。

先交付 LoRA 可用的测试版本，再合并预览和必要的稳定性修复。正式 1.6.0 发布前回归无 LoRA 生图、启用/关闭、权重变化、缓存失效、取消重启和已有模型保留。各测试版本与 1.5.11 正式版分开管理。

## 首轮原型结果（2026-09-06）

独立开发分支为 `feature/1.6-lora`，来自 1.5.11 正式源码提交。代码位于 `experiments/lora/`，没有改动正式 APP 或模型。

标签、runtime 子目录、Safetensors 头部结构、矩阵配对、训练 alpha/rank 与用户强度的区分、双 LoRA 权重增量及归零恢复共 41 项主机检查通过。文件扫描仅把结构可读者标成待 QNN 模板适配；识别到文件不意味着可在 NPU 执行。

五算子小模型在 ONNX Runtime CPU 上验证强度 0、0.8、1.1、-0.4、再次 0，最大绝对误差约 5.96e-8，两个零强度结果与基线相同。QAIRT 2.48 的 float_only 转换保留 `lora_A`、`lora_B` 两份可更新静态权重，离线编译得到 50,096 bytes 的 SM8750 HTP context，官方 utility 成功解析，并确认 `lora_alpha` 输入仍在。此结果证明该最小图的离线准备路径成立，未执行手机 NPU、未调用 adapter binary 热切换，也尚未证明完整 WAI 的 LoRA 兼容。

下一断点是小图 adapter binary 的生成/替换验证，然后将同一机制映射到 WAI 的实际层名、形状及支持的 LoRA 秩。标准 UNet/CLIP 的现有冻结 context 不能直接当成已经支持任意 LoRA。需要新的可更新底模时，重型模型编译仍交给 workstation，APP 工作继续在 desktop。

## 1.6.0-alpha.1 实验与测试包（2026-09-06）

测试包使用独立 applicationId `com.geniex.demo.loratest`，名称为“Rin LoRA 1.6 测试”，versionCode 18。它与 1.5.11 并列安装，启动 LoRA 实验室，不替换正式生图应用，不重下或改写现有 WAI 模型。

当前主测试是动态 A/B 权重输入。五算子的合成线性图保留 `sample [1,8,32]`、`lora_A [32,8]`、`lora_B [8,32]`、`lora_alpha [1,1,1]` 四个输入；7 组 CPU 数值检查通过，50,360-byte context 经官方 utility 确认为 SoC 69 / DSP V79。该路线尚未进行手机 NPU 验证，更不等于完整 SDXL LoRA 已可用。

对照测试使用 50,096-byte 底模和三份各 25,744-byte 预编译适配器。全部经官方工具验证为 SoC 69 / V79。JNI 在同一 context 中执行七组测试，真实调用 contextApplyBinarySection，并检查恢复后的数值。带 enable_weights_updates 的 Conv 小图在二次整理图时失败，四维 alpha 变体也失败；一个线性小图在 compose 阶段失败。记录的是这些具体用例，不能推广为该 SDK 不支持所有 LoRA。

测试 APP 已实现 runtime 子目录创建、后台 Safetensors 文件头检查、直接 LoRA 强度标签、两种自测入口和报告分享。候选文件显示“待 WAI 适配”，不把解析成功当作已可生成。21 项真实 Kotlin/JUnit 检查通过；APK 包含 19 个适配器路线素材和 30 个动态路线素材，逐项 SHA 校验通过。NDK、Kotlin、DSP 原字节恢复、历史证书签名均成功。手机界面和 NPU 结果仍待用户确认。

下一验收点：手机安装测试包，授予文件权限，暂停正式版生图，运行“开始动态 LoRA NPU 自测”，再分享报告。动态路线通过后才准备完整 WAI 的固定秩/多适配器模板、层名映射和真实 LoRA 数值及成图验证。当前自测的 A/B 矩阵是内置合成数据，还不能将扫描到的用户文件用于 WAI 生图。实时预览和普通词 embedding 权重保持待实施状态。
